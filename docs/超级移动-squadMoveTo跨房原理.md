# squadMoveTo 跨房原理

## 前提：formalize 把房间坐标变成全局大坐标

按 `parseRoomName` 的规则，`halfWorldSize = 255 >> 1 = 127`：

- East 房间：`baseX = (127 + ewNum + 1) * 50`
- West 房间：`baseX = (127 - ewNum) * 50`

以 **E59N31 → E60N31** 为例：

```
E59N31: baseX = (127 + 59 + 1) * 50 = 9350
E60N31: baseX = (127 + 60 + 1) * 50 = 9400
```

相邻房间边界差了 **51**，不是 1。

```
E59N31 x=49  →  formalX = 9350 + 49 = 9399
E60N31 x=0   →  formalX = 9400 + 0  = 9400
```

## 场景：向右跨房

四人在 E59N31 排成 2×2 正方形，leader 是右下角 C2(49,49)：

```
E59N31:
    C1(48,49)  C2(49,49)=leader
    C0(48,48)  C3(49,48)
```

各点的 formalX：

| 角色 | 坐标 | formalX |
|------|------|---------|
| C0 | E59N31(48,48) | 9350 + 48 = **9398** |
| C1 | E59N31(48,49) | 9350 + 48 = **9398** |
| C3 | E59N31(49,48) | 9350 + 49 = **9399** |
| C2 | E59N31(49,49) | 9350 + 49 = **9399** |

`squadStepToPos` 里，下一步 `leaderNextPos = E60N31(0,48)`，formalize 后 formalX = **9400**。

如果直接计算队友目标 `formalPos + (队友.formalX - leader.formalX)`：

| 队友 | 当前 formalX | xdiff | 目标 formalX | 解码 |
|------|-------------|-------|-------------|------|
| C0 | 9398 | **-1** | 9400+(-1)=**9399** | ❌ E59N31(49,?) — 非法！ |
| C1 | 9398 | **-1** | 9400+(-1)=**9399** | ❌ E59N31(49,?) — 非法！ |
| C2 | 9399 | 0 | 9400 | E60N31(0,49) |
| C3 | 9399 | 0 | 9400 | E60N31(0,48) |

C0、C1 实际还在 E59N31，但代码用 E60N31 的 formalX=9400 当基准去算目标，减出来的 xdiff=-1 指向 9399——tile2Pos 解码出来根本不是一个合法的 2×2 正方形站位。

## 引擎跳房的真实时序

Screeps 引擎在 tick 末处理移动时，**站在 x=0 或 x=49 的 creep 会被传送到相邻房间的对应 x 坐标**。四人同时移动，但只有 x=49 的两个成员会触发跳房。

### T0：两人先到边界

```
移动前:  C0(48,48)  C1(48,49)  C2(49,49)  C3(49,48)
移动后:  C0→(49,48) C1→(49,49) C2→E60N31(0,49) C3→E60N31(0,48)
```

C2、C3 被传送到 E60N31，C0、C1 还在 E59N31，只是移到了 x=49。

### T1：剩下两人跟上

```
移动前:  C0(49,48) C1(49,49) C2(E60N31,1,49) C3(E60N31,1,48)
移动后:  C0→E60N31(0,48) C1→E60N31(0,49) C2→E60N31(2,49) C3→E60N31(2,48)
```

C0、C1 也被传送到 E60N31。此时四人全部进入新房间。

### T2：四人继续前进

```
移动前:  四人都在 E60N31，leader 在 (2,49)
移动后:  leader→(3,49)，其他人跟随
```

此时四人同处一个房间，xdiff 始终是 0 或 -1，目标计算完全正确。

## 为什么需要 xdiff=-1/-2 检测？

xdiff=-1/-2 检测只在 **leader 还在旧房间、path 下一步已经进入新房间** 的那一刻拦截。

```js
if (xdiff === -1 && leader.pos.x === 49 && formalPos.x > leaderPos.x) {
    squadMove(squad);  // 原地待命
    return OK;
}
```

- `xdiff === -1`：队友 formalX 比 leader 小 1（正常同房间内是正方形左边两格）
- `leader.pos.x === 49`：leader 还在旧房间右边界
- `formalPos.x > leaderPos.x`：path 下一步 formalX 更大（向右跨房）

三个条件同时满足，说明 **leader 还没跨房，但 path 已经给出新房间的下一步**。此时如果直接计算队友目标，会把队友算到非法坐标。所以调用 `squadMove(squad)` 让小队原地待命。

注意：`moveOneStepSquad` 已经在调用 `squadStepToPos` 之前执行了 `creepCache.idx++`，所以 path idx 已经往前推了。

## 为什么 leader 进入新房间后不需要等待？

T1 开始时，leader 已经在 E60N31(0,48)。此时 xdiff 仍然是 -1，但条件 `leader.pos.x === 49` 不再满足（leader 的 x=0），所以不拦截。

这是因为 **引擎的跳房机制让小队自然流过边界**：

1. T0 末：C2、C3 在 E60N31，C0、C1 在 E59N31(x=49)
2. T1：C2、C3 往前走，C0、C1 移到 C2、C3 T0 末的位置
3. T1 末：C0、C1 也被传送，此时 C2、C3 已经不在 (0,48)/(0,49)，而是在 (1,49)/(1,48)
4. T2：四人全部在 E60N31，队形自然恢复

leader 进入新房间后，虽然 C0、C1 还在旧房间，但他们的 formalX 是 9398/9399，leader 的 formalX 是 9400/9401。此时 `squadStepToPos` 计算的 xdiff 不再是 -1，而是 **-2/-1**（因为 leader 已经走出 0 边界）。

等等，让我重新算。T1 时 leader 是 C2(C2 在 E60N31(0,49) 还是 C3 在 (0,48)？)

实际上，T1 开始时四人位置：
- C2: E60N31(0,49), formalX=9400, formalY=4800+49=4849
- C3: E60N31(0,48), formalX=9400, formalY=4800+48=4848
- C1: E59N31(49,49), formalX=9399, formalY=4849
- C0: E59N31(49,48), formalX=9399, formalY=4848

`squadMoveTo` 重新选 leader：x+y 最大的是 C2(9400+4849=14249) 和 C1(9399+4849=14248)，所以 **leader 是 C2**。

path idx 已经推进，下一步是 E60N31(1,48)，formalX=9401。

| 队友 | 当前 formalX | xdiff | 目标 formalX |
|------|-------------|-------|-------------|
| C0 | 9399 | **-1** | 9401+(-1)=**9400** | E60N31(0,?) |
| C1 | 9399 | **-1** | 9401+(-1)=**9400** | E60N31(0,?) |
| C2 | 9400 | 0 | 9401 | E60N31(1,49) |
| C3 | 9400 | 0 | 9401 | E60N31(1,48) |

C0、C1 的目标 formalX=9400，对应 E60N31(0,?)。但 C0、C1 实际在 E59N31(49,48)/(49,49)。

这里有个微妙的问题：C0、C1 在 T1 的移动目标是 E59N31(49,48)/(49,49)（即 C2、C3 T0 末的位置），而不是 E60N31(0,?)。

**所以 xdiff=-1/-2 检测在 leader 进入新房间后仍然可能触发？**

不，T1 时 `leader.pos.x === 0`，不满足 `leader.pos.x === 49` 的条件，所以不拦截。这意味着代码在 T1 时会把 C0、C1 的目标算成 E60N31(0,?)，但实际移动时 C0、C1 会被传送回 E60N31(0,?)——**恰好是对的**！

因为 C0、C1 在 E59N31(49,48)，向右移动会被传送到 E60N31(0,48)。而代码算出的目标 formalX=9400 对应 E60N31(0,?)，y 方向也匹配。所以 **即使没有拦截，结果也是正确的**。

这就是为什么 xdiff=-1/-2 只拦截 leader 在旧房间的情况：一旦 leader 进入新房间，引擎的跳房机制会自动把剩余两人送到正确位置。

## `squadMove(squad)` 的作用

`squadMove(squad)` 不带 target 参数时，会对每个队员注册 `registerMoveIntent(creep, 0)`。在 `endTickResolve` 中，target=0 意味着 `noMove = true`，形成 score = `ultraMoveScore` 的 superTarget，目标就是当前自身位置——**小队停在原地**。

## 完整流程

| Tick | leader 位置 | xdiff 检测 | 动作 |
|------|-----------|-----------|------|
| T0 | E59N31(49,48) | xdiff=-1, `leader.pos.x===49` 且下一步向右 → **命中** | `squadMove(squad)` 原地待命，idx++ |
| T0 末 | 仍在 E59N31(49,48) | — | 引擎没移动 |
| T1 | E60N31(0,48) | xdiff=-1, 但 `leader.pos.x===0` 不触发 | 正常计算目标，`squadMove(squad, targets)` |
| T1 末 | 进入 E60N31(0,48) | — | 引擎执行移动，C0/C1 被传送 |
| T2 | E60N31(1,48) | xdiff=0/-1, 同房间 | 四人继续前进 |

## 一句话总结

> `xdiff=-1` 在正常同房间内是对的，但在 leader 还在旧房间边界、path 已经进入新房间时，它变成了**"基准坐标从 9399 跳到 9400，但队友还是 9398"**的信号。代码等一 tick 让引擎完成第一次跳房，之后小队就自然流过边界，不再需要拦截。
